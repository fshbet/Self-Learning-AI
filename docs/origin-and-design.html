How this idea was found, and how the design was derived

The platform did not start from a technology. It started from a question about trust, and every part of the design can be traced back to that question in a few steps. This document walks the chain from the original problem to the running system.

The starting question

"Can an AI system keep itself up to date with reliable, specialised knowledge — first about Power BI, later about anything — without anyone having to retrain it, and without it quietly learning things that are wrong?"

The obvious answer in 2026 is "fine-tune a model on the documentation." The founding insight of this project is that this obvious answer is the wrong place to start. A model that has "learned" Power BI is a snapshot: it cannot tell you where a claim came from, it cannot notice when Microsoft changes a page, and when two sources disagree it simply picks one — confidently. The problem was never that models lack knowledge. The problem is that knowledge has to be collected, checked, versioned and kept current, and a model is the wrong container for that.

Five observations that shaped the idea

1 · Models are confident, not correct

A language model will produce a fluent answer whether or not it knows. Confidence has to come from somewhere outside the model.

2 · Technical knowledge expires

Product versions, renamed features ("dataset" → "semantic model"), deprecated functions. A fact is only true for a version, at a time.

3 · Volume is not truth

Scrapers collect everything and learn nothing. Ten blogs repeating one Microsoft page are one piece of evidence, not ten.

4 · Training freezes and hides

Fine-tuning is expensive, freezes the snapshot, and makes provenance impossible to recover. It should be the last step, if ever.

5 · Every domain is different, the machinery is not

Power BI, Tableau, a robot arm: the taxonomies and validators differ completely, but discovering, collecting, verifying, versioning and retrieving are the same jobs.

The one principle everything hangs from

Build the knowledge infrastructure first; keep the AI model replaceable.

Once you accept that the knowledge — not the model — is the asset, the rest of the design is not a list of features to choose from. It is a set of consequences. The sections below show each design decision as a derivation from the principle and the observations.

Deriving the design, step by step

Consequence 1 — Evidence over confidence (from observation 1)

If confidence cannot come from the model, it must come from evidence. Therefore every knowledge item must point to a specific place in a specific document. The platform makes this a hard rule: the extractor must copy a verbatim quote, the quote is located in the page, and if it cannot be found the item is discarded. A confidence score is then computed from named, stored factors (source authority, verified evidence, agreement, specificity, validation) so a person can always see why a number is what it is.

Consequence 2 — Versioning over overwriting (from observation 2)

If facts expire, the system must know when a fact was collected, when it was last verified, and which product version it applies to — and it must never destroy the old state. Hence: content hashes and conditional requests to detect change cheaply; items whose evidence vanished from a changed page become stale rather than deleted; every status change is written to an audit trail.

Consequence 3 — Research over crawling (from observation 3)

If volume is not truth, the collector must be selective and must weigh sources. That produced the source registry (every website has an authority level, permissions and a scope), relevance-driven crawling instead of "download everything", and the rule that a second source repeating a statement becomes additional evidence on the same item rather than a duplicate. The same reasoning produced conflict records: when sources disagree, keep both and ask a person.

Consequence 4 — Controlled learning over self-training (from observation 4)

If training freezes and hides, then "self-updating" must mean updating the repository, not the model. The improvement loop is: extract → evaluate against a golden question set → find the failure → fix retrieval, prompts, rules or sources → re-evaluate. Fine-tuning is explicitly deferred to a later phase, and the repository is designed so that it could produce training data with a license manifest if that day comes.

Consequence 5 — Domain plugins over domain-specific platforms (from observation 5)

If the machinery is the same but the domains differ, the core must not know what Power BI is. Everything domain-specific — taxonomy, terminology, seed sources, validators, skills, test questions — lives in a plugin folder behind one contract, and contract tests make sure the core cannot drift into knowing about one domain. Adding a topic is adding a folder.

Consequence 6 — The model as orchestrator, not oracle

Combining all of the above: the model reads sections and proposes facts, judges whether two statements contradict, and writes answers — but only from items it is handed, and only with citations. The repository is the source of truth; the model is a replaceable worker whose every call is metered. Content pulled from the web is treated as data, never as instructions, which is also the platform's defence against prompt injection.

Consequence 7 — Local first, portable always

A knowledge asset should not be hostage to a vendor. Every external dependency (model, embeddings, storage, search) sits behind an adapter with a local default (Ollama, filesystem, PostgreSQL, SearXNG), and the identity of the model that produced each artefact is stored with it. Moving to a cloud provider later is configuration, not a rewrite.

The guiding analogy

The design document ends with the image that ties it together: the system should behave less like a scraper and more like a continuously maintained research organisation. A good research team discovers sources, reads selectively, cross-checks, keeps notes with citations, flags disagreements for a senior reviewer, revisits topics when the world changes, and measures itself. Every screen in the app corresponds to one of those activities — Sources, Documents, Knowledge, Review, Pipeline — and the one thing such a team never does is publish a claim it cannot cite.

From document to code

The idea was first written down as a 45-section design document. Turning it into software followed the document's own advice:

  1. Review the design against industry practice before building. This added the parts a specification needs to be buildable: non-functional requirements, a plugin contract, a knowledge-item schema and status-transition table, responsible collection rules, observability, a testing strategy, risks, and phase exit criteria.
  2. Decide where to run it. Free cloud tiers could host the serving side, but long crawls and unlimited local model calls favoured a local-first build on a workstation with a GPU — with adapters so the choice is reversible.
  3. Build Phase 1–3 as one vertical slice: plugin contract → responsible collector → extraction with mandatory evidence → scoring and lifecycle → hybrid retrieval and cited answers → a UI that exposes the evidence trail everywhere.
  4. Verify against reality: a database-backed integration test with recorded pages and a fake model, then a live run against Microsoft Learn with a real local model.

What building it taught us

The first live run produced 43 facts from two pages, all with verbatim evidence — and immediately demonstrated why the principles matter, because the system's own safeguards caught three mistakes in the first implementation:

What happenedWhy the principle mattered
The contradiction detector opened 28 "conflicts" between statements like "the DAX reference covers filter functions" and "…covers statistical functions". A list is not a disagreement. Because conflicts are surfaced rather than silently resolved, the false positives were visible at once. The fix derived from the design: items from the same document do not conflict, predicates with many values are lists, and remaining pairs are adjudicated before a conflict is opened.
Near-duplicate detection merged CLOSINGBALANCEWEEK into OPENINGBALANCEWEEK because their sentences were almost identical. Similar wording is not the same fact. The audit trail showed exactly which items had been folded and why, so they could be restored. The rule now requires the same subject, equivalent objects and lexical overlap — vector similarity alone is not evidence.
Documentation hub pages yielded a single page each. Relative links were resolved against the wrong base URL. Visible immediately in the per-source crawl statistics that the observability requirement had put on the Pipeline page.

None of these were found by unit tests; all were found because the system records what it does and why. That is the practical meaning of "evidence over confidence".

Where it goes next

The design document lays out the remaining phases, each an explicit test of the principle:

  • Executable validators (sandboxed) — test a DAX example against a real model instead of asking a model to judge it.
  • Source reliability history — authority that is earned over time, not only declared.
  • Golden-set evaluation runner — every change to prompts, rules or models is measured before it is promoted.
  • A second, then a radically different domain (Tableau, then robotics or an industrial machine) — the proof that the core is genuinely generic. If a new topic ever needs a change in the core, that is a bug in the architecture, not a feature.

Power BI is simply the first domain used to prove the platform. The idea is the machinery; the topics are plugins.
